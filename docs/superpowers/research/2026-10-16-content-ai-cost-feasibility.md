# 内容 AI 增强费用与 2核2G 可行性评估
日期：2026-10-16。性质：研究建议，不修改现网配置、业务合同或发布状态。

## 结论
现有 2核2G 服务器可承担云端模型 API 的排队、调用、校验、缓存和落库；这不等于在服务器本地运行模型。建议复用现有 Node SYSTEM Collection Runtime 和 Model Gateway，初始 AI 并发 1，与采集、网页请求错峰调度。尚无压力测试数据，不能保证具体吞吐量。无需仅为调用 API 立即升级服务器。

首选复用现有内容理解能力，将中文标题、答案先行摘要、阅读推荐理由、类型/相关性判断合成一次结构化调用；规则筛重和候选召回在前，模型只判断少量模糊聚类候选。全文翻译优先对入选文章或用户请求文章执行。AI 增强不会自行增加来源覆盖，仍需落实前一份采集评估中的来源补齐、调度和失败恢复。

## 当前代码事实
- lib/server/content/content-understanding-enrichment.ts 已有 titleZh、summaryZh、editorialJudgment、类型/作者角色/标签/事实提取与校验；editorialJudgment 是阅读价值建议，不是精选或热点最终状态。
- 该入口已有输入哈希与版本缓存、一次结构修复，并对有正文的材料另调翻译。若直接对所有 Raw 启用，会跟随产生所有外文正文的翻译费用，需要先拆分触发策略。
- 现有正文候选截到 18,000 字符；理解输入再截到 12,000 字符。因此现有方法不保证任意长度文章的完整翻译。真正全文需取得完整正文、分块翻译、校验完整性、拼接，并明确 PARTIAL。
- lib/server/ai/configured-chat.ts 当前调用未保存供应商 usage，亦未显式控制 thinking 与 max_tokens；接入低成本方案时应补实际 token 账本、任务输出上限和模式选择。
- 当前自动采集边界不调用此 AI 入口；deploy/systemd/opc-collection.service 清除 AI 环境变量，采集进程 MemoryMax=512M、CPUQuota=50%。自动增强属于后续 Decision Brief 和产品合同调整，不是已有自动能力。
- 当前规则聚类、Event Momentum、精选确定性门槛不产生模型 token。不得为了“加 AI”把所有判断替换成模型或让模型直接拥有事实/发布状态。

## 用量假设与公式
以下是预算假设，非项目实测；中文字符数不等于 token 数。
- 每条去重后的候选：一次标题+摘要+理由+分类/价值判断，3,000 输入、600 输出 tokens，包含提示词和材料。
- 20% 候选需要模型辅助聚类，每个模糊候选仅判断一个候选关系，1,500 输入、100 输出。若每条比较 k 个关系，此部分按 k 倍增加；禁止全量两两比较。
- 每篇全文翻译：4,500 输入、5,000 输出 tokens，代表一篇中等长度文章；长文分块和上下文重复会增加成本。中文原文无需翻译。
- 每月 30 天；“每天 N 条”是去重后真正送入 AI 的候选量，不是请求量或页面条数。正文哈希不变直接复用结果。

每日 N 条、10% 翻译的月 token：输入 0.1125N 百万、输出 0.0336N 百万。
每日 N 条、全部翻译的月 token：输入 0.234N 百万、输出 0.1686N 百万。
费用 = 输入未命中百万数×单价 + 输入命中百万数×单价 + 输出百万数×单价。

| 每日 AI 候选 | 10% 候选全文翻译/月 | 全部候选全文翻译/月 |
|---:|---:|---:|
| 100 | ¥24.69–49.38 | ¥90.84–181.68 |
| 300 | ¥74.07–148.14 | ¥272.52–545.04 |
| 1000 | ¥246.90–493.80 | ¥908.40–1816.80 |

以上已含合并语义调用与有限聚类，不含采集/搜索/正文提取服务、已有服务器费用、存储备份与人工运营。建议在估值上另留 30% 预算用于修复、重试和分块开销；这不是费用上限。每天 300 条时约为 ¥96–193/月（10% 翻译）或 ¥354–709/月（全翻）。内容长度翻倍、额外推理、额外候选关系比较会继续增加费用。

按空闲价，合并理解约 ¥0.0054/条；一次有限聚类判断约 ¥0.0019；一次上述长度翻译约 ¥0.0245/篇，高峰均二倍。与一条材料全部做几次重复理解相比，先合并输出和缓存通常更有收益。

## 建议执行边界
1. 先机械去重、时间与主题过滤，再调用合并语义任务。Prompt 输出字段分开事实、摘要、推荐理由、相关性与不确定性，不把“模型认为重要”当作 Hotspot Authority。
2. 聚类先按 URL、实体、动作、版本、时间召回有限候选；模型判 SAME_EVENT / RELATED / DIFFERENT 等关系，由 Core 校验和更新。不同版本/不同发布日期不能因标题相似强合并。不新增全量 LLM 两两聚类，也不假设当前已有 Embedding 服务。
3. 关键快讯及时处理；长文翻译可低优先级在空闲时段处理，不为省钱拖慢重要事件发现。标题不足时返回材料不足，不编造摘要与理由。
4. 翻译缓存按原文身份与正文哈希、语言、Prompt/模型版本；事件聚类后仍保留各篇文章的原文和翻译，不用一篇译文冒充所有来源。
5. 设置请求级输出上限、超时、有限重试、每日金额/token 上限、队列背压；按 usage 分别记输入命中/未命中、总输出、模型和任务。推理 tokens 是总输出细分，避免双计。不要仅按最终显示字数记账。
6. 沿用现有 Runtime 与 Gateway，以受控后台任务执行，页面读缓存；不增加 Python/FastAPI/APScheduler 第二执行主链，也不把 AI 放入海外 Deno Relay。
7. 初期并发 1，待监控 CPU/RSS、数据库延迟、队列长度和实际 token 后再考虑 2；单次只保留当前文章/块，避免批量全文驻留。现有 512M 采集进程限制需一起验证，不宜直接增加无界任务。
8. 本地 7B 模型即使只按 4-bit 权重计算也约 3.5GB（十进制），尚未含运行时/KV cache；2GB 内存且与 Web/PG 共机不适合部署。小模型需另外实测质量与吞吐，不能默认替代生产翻译和判断。

## 选择与验证
推荐起步：每日最多 300 条唯一候选、10% 全文翻译、非思考 Flash、有限聚类；月度模型预算先设 ¥200。预算不代表花满，实际按进入 AI 的条数和 token 计费。若必须全量翻译，以 ¥700–800 月预算起步再按真实文章长度修订。

先取 100–200 篇有代表性的材料离线评估：中文/英文、快讯/长文、模型版本发布、教程/评论、重复转载及不同事件同名。记录真实性、动作类型保留、摘要答案先行、理由有依据、完整翻译率、错误合并率、漏合并率、实际 tokens、P95 耗时和失败率。重要错误不得用低均价掩盖。先验证输出质量，再决定少量复杂材料是否升级更贵模型。

本报告没有执行收费请求、采购、部署或自动启用 AI。
