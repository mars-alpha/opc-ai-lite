# T4-01 — 哪些重复工作值得系统化，哪些反而不该动

Primary Knowledge Home: **自动化价值判断（Automation Suitability）**
Lesson Type candidate: **APPLICATION**
Canonical learner result: 能判断一条已经人工跑过的业务链是否值得进入系统化设计，并把理由、风险和暂不系统化的边界说清楚。

## Learner problem

看到重复工作后，常见反应是“既然重复，就自动化”。但真正的问题是：
- 这件事是否真的经常发生；
- 人工做法是否已经相对稳定；
- 规则和输入是否足够清楚；
- 做错一次的成本有多大；
- 系统化后是否真的节省时间、减少遗漏或提升一致性。

## Core judgment

**重复，不等于值得系统化。只有“经常发生 + 做法相对稳定 + 输入输出说得清 + 系统化有实际价值 + 风险可控”的工作，才值得进入下一步设计。**

至少判断五件事：
1. 是否反复发生；
2. 人工做法是否已经跑通并趋于稳定；
3. 输入、判断和结果是否能说清；
4. 系统化能解决什么真实成本；
5. 出错时的影响是否在可接受范围内。

## Step 1 — 建立直觉

只建立一个直觉：

> **越混乱、越不稳定的工作，越不应该因为“麻烦”就急着自动化。**

可用轻量例子：
同一个自媒体账号每天都要整理新闻；“从固定来源收集并整理成候选清单”已经重复稳定，而“最后哪三条值得发、为什么值得发”仍高度依赖当天业务判断。两部分不能因为都很耗时间就一起自动化。

Step 1 不展开完整评分框架。

## Step 2 — 讲透方法

完整案例使用 AI 日报业务链：
- 来源收集；
- 去重；
- 判断是否与账号定位相关；
- 选出重点；
- 提炼观点；
- 人工审核；
- 发布。

要求比较三类环节：
- 重复且规则稳定；
- 重复但判断仍不稳定；
- 低频但高风险。

讲清楚为什么“耗时间”不是唯一标准，并展示：
**重复性 → 稳定性 → 可描述性 → 价值 → 风险** 的判断顺序。

## Step 3 — 检查理解

1. **SINGLE_CHOICE / BEST_JUDGMENT**
   哪一种工作最适合优先进入系统化设计：高频、规则清楚、结果可检查，而不是“最讨厌做”的工作。

2. **TRUE_FALSE / MISCONCEPTION**
   “一项工作只要每天重复，就应该全部交给 AI 自动完成。” → 错。

3. **MULTI_SELECT / BOUNDARY_CONDITIONS**
   判断是否值得系统化应关注：重复频率、人工流程稳定程度、输入输出是否清楚、可获得价值、出错风险；不把“看起来很先进”作为理由。

## Step 4 — 实操

练习产物：**系统化候选判断卡**

真实背景提供一条自媒体业务链，例如：
“每天收集 30 条 AI 新闻 → 去重 → 选 3 条 → 写观点 → 审核 → 发布”。

Reference Fill 必须形成完整任务，要求 AI：
- 按步骤列出当前人工流程；
- 对每一步判断重复性、稳定性、输入输出清晰度、可获得价值和出错风险；
- 给出“优先系统化 / 暂时保留人工 / 先继续验证”的候选建议；
- 每个建议说明依据；
- 把缺少的信息单独列出；
- 不虚构历史耗时、错误率、成本、转化或业务数据；
- 不直接设计自动化工具和系统。

## Step 5 — 复盘判断框架

must-retain judgments：
- 重复只是必要条件之一，不是充分条件；
- 人工流程没有跑稳定之前，自动化只会把混乱放大；
- 系统化价值必须落到时间、遗漏、一致性、规模或风险等真实结果；
- 高风险、规则不清、经常变化的判断应保留人工或继续验证；
- AI 可以帮助整理候选和比较条件，但不能替业务负责人决定风险是否可接受；
- “暂不系统化”是合理结果，不代表这项工作没有价值。

## Step 6 — 能力获得

Capability Gain：
> 我能判断一项重复工作现在是否值得系统化，并说清为什么做、为什么暂时不做。

Self Assessment：
- 我不会再把“重复”直接等同于“应该自动化”；
- 我能说清稳定性、价值和风险如何影响判断；
- 我能指出哪部分适合先系统化、哪部分继续保留人工。

Trigger Scenario：
> 当你发现一项工作每天都在重复，很想马上找工具自动化时，这节课用于先判断它是否已经稳定到值得系统化，避免把一个还没想清楚的流程直接固化。

Next Lesson Value：
> 选出值得系统化的业务链后，下一步要把人平时“凭经验做”的过程拆成系统真正能理解和执行的步骤。

## Anti-repeat / boundary

- ≠ T3-15：T3-15 决定下一轮业务动作；T4-01 判断其中哪些稳定重复链值得系统化。
- ≠ Track 05 Business Case：本课只做流程级系统化价值判断，不做完整方案 ROI、预算、组织决策。
- 不教 n8n、Make、Zapier、Dify 等平台选择。
- 不设计节点、触发、API 或代码实现；这些属于后续课。

# T4-02 — 一条人工流程，怎么拆成系统真正能执行的步骤

Primary Knowledge Home: **流程拆解 / 输入-处理-判断-输出-检查**
Lesson Type candidate: **APPLICATION**
Canonical learner result: 能把一条人工已经跑通的业务流程拆成顺序明确、输入输出清楚、包含判断和检查的工作流步骤。

## Learner problem

人做事时会自动补很多隐含信息，例如：
- “先看一下今天有什么新闻”；
- “觉得有价值的留下”；
- “差不多了就发”。

这些表达对人可能够用，但系统不知道：
- “看什么”；
- “留下”的条件是什么；
- 中间产生什么结果；
- 谁判断；
- 怎么知道这一步完成。

## Core judgment

**系统能执行的流程，不是把人工动作写得更细，而是把每一步的“输入 → 处理 → 判断 → 输出 → 检查”说清楚。**

拆解时优先判断：
1. 这一步从哪里拿到什么；
2. 做什么处理；
3. 是否存在判断分支；
4. 产生什么可交给下一步的结果；
5. 怎么检查这一步是否完成。

## Step 1 — 建立直觉

只建立一个直觉：

> **“我平时就是这么做的”不等于系统知道怎么做。**

可用轻量例子：
“整理新闻”对人是一个动作，对系统至少涉及“拿到候选 → 去重 → 标记来源 → 输出候选清单”。

不在 Step 1 展开完整五项结构。

## Step 2 — 讲透方法

完整案例使用“AI 新闻 → 公众号文章”人工流程：

原始说法：
“每天找新闻，选重要的，写一下，审核后发。”

拆成：
- 输入：当天来源清单；
- 处理：收集并去重；
- 输出：候选新闻清单；
- 判断：是否符合账号关注方向、是否有可靠来源；
- 输出：入选清单；
- 处理：整理事实与观点草稿；
- 检查：来源是否齐全、事实是否与原文一致；
- 人工判断：最终是否发布。

重点展示：
- 动作与判断不是一回事；
- 每一步都要有明确结果；
- 检查不是最后才做；
- 不需要一开始就画复杂流程图。

## Step 3 — 检查理解

1. **SINGLE_CHOICE / BEST_JUDGMENT**
   哪个拆法更适合系统执行：有明确输入、动作、结果和判断，而不是“分析一下再处理”。

2. **TRUE_FALSE / MISCONCEPTION**
   “把一个人工流程拆成越多步骤越专业，所以步骤越细越好。” → 错。

3. **MULTI_SELECT / BOUNDARY_CONDITIONS**
   一个可执行步骤通常需要哪些：输入、处理、判断条件（如有）、输出、检查；不要求每一步都调用 AI。

## Step 4 — 实操

练习产物：**人工流程拆解表**

Reference Fill 使用真实自媒体场景，例如：
“每周把一篇核心文章复用成公众号短文、视频脚本和口播提纲，目前由一个人手工完成。”

要求 AI：
- 先复述当前人工流程，不补写不存在的步骤；
- 按自然业务边界拆成若干步骤；
- 每一步写清输入、处理、是否需要判断、输出、检查方式；
- 标记哪些步骤信息不够，需要人工补充；
- 不决定使用什么自动化平台；
- 不替业务新增审批、工具、数据源或规则；
- 如果拆得过细，合并成仍然可检查的最小步骤。

## Step 5 — 复盘判断框架

must-retain judgments：
- 拆流程不是把句子切碎，而是找到有清楚输入和结果的业务步骤；
- “处理”与“判断”必须区分；
- 每一步的输出要能成为下一步可使用的输入；
- 检查应出现在关键步骤，而不是只在最后补救；
- AI 可以协助整理已有人工做法，但不能凭空补出业务规则；
- 并非每一步都需要 AI，有些步骤更适合确定规则或人工判断。

## Step 6 — 能力获得

Capability Gain：
> 我能把一条“人知道怎么做”的业务流程，拆成系统也能理解的清楚步骤。

Self Assessment：
- 我能为每一步说清输入和输出；
- 我能区分处理动作和判断动作；
- 我能发现“这一步其实还靠人的隐含经验”。

Trigger Scenario：
> 当你想把一项已经稳定的人工作业交给自动化，但发现描述只能写成“整理一下、判断一下、处理一下”时，这节课用于把隐含做法拆成可执行步骤。

Next Lesson Value：
> 步骤拆清以后，系统还需要知道什么时候应该开始执行；下一课会定义启动条件和不启动边界。

## Anti-repeat / boundary

- ≠ T1-16 Workflow 概念课：这里不是理解什么叫 Workflow，而是拆真实人工业务链。
- ≠ T2-15 SOP-lite：T2-15 让人可以复用方法；T4-02 进一步把方法拆成系统执行所需的步骤和交接边界。
- 不进入状态保存、失败恢复、外部工具连接；这些在后续课。

# T4-03 — 系统什么时候开始做，什么条件下才应该启动

Primary Knowledge Home: **触发条件（Trigger）与启动边界**
Lesson Type candidate: **APPLICATION**
Canonical learner result: 能为一条工作流定义清楚的启动事件、必要条件、不启动条件和启动时需要的最小输入。

## Learner problem

流程已经拆清楚后，仍然会出现一个关键问题：

“它什么时候开始？”

模糊表达包括：
- “有新内容就跑”；
- “每天自动执行”；
- “客户发消息就处理”。

但真实业务里还需要判断：
- 什么才算“新内容”；
- 每天几点、是否节假日都运行；
- 哪类消息应该触发，哪类不应该；
- 启动前是否已经具备必要信息；
- 同一件事是否已经处理过。

## Core judgment

**触发不是“定一个时间”或“收到一个事件”这么简单，而是：发生了什么 + 必要条件是否满足 + 哪些情况明确不启动。**

启动设计至少包含：
1. 启动事件或时间；
2. 必要前置条件；
3. 不启动条件；
4. 启动时必须已经有的最小输入；
5. 对重复事件的基本识别意识（深入保护机制留 T4-11）。

## Step 1 — 建立直觉

只建立一个直觉：

> **系统最危险的错误之一，不是“没开始”，而是在不该开始的时候开始。**

轻量例子：
“收到私信就自动生成销售跟进”看起来方便，但普通咨询、合作邀约、售后问题和垃圾消息不应该全部进入同一流程。

不在 Step 1 展开完整触发规则表。

## Step 2 — 讲透方法

完整案例使用“AI 日报候选收集”：

候选触发方式：
- 每天固定时间；
- 监测到来源新增内容；
- 人工点击“开始今天日报”。

比较三种方式的适用条件，并设计：
- 事件：什么时候认为应该启动；
- 前置：来源清单是否存在、日期是否明确；
- 不启动：当天已完成、来源不可用、人工暂停；
- 最小输入：日期、来源范围、账号关注主题；
- 启动结果：生成一轮新的候选收集任务。

重点让学员理解：
**触发负责决定“要不要开始”，不负责把后面的整个流程都写完。**

## Step 3 — 检查理解

1. **SINGLE_CHOICE / BEST_JUDGMENT**
   哪个触发定义最清楚：同时写出事件、必要条件和不启动情况。

2. **TRUE_FALSE / MISCONCEPTION**
   “只要设置每天 9 点运行，就已经完整定义了一个可靠触发。” → 错。

3. **MULTI_SELECT / BOUNDARY_CONDITIONS**
   启动规则可能需要：事件/时间、必要条件、不启动条件、最小输入、重复事件意识；不要求在这里设计后续每个节点。

## Step 4 — 实操

练习产物：**启动条件卡**

Reference Fill 提供真实业务背景，例如：
“当有人通过内容页填写需求表单后，团队希望开始线索整理流程。”

要求 AI：
- 区分什么事件代表“新线索到达”；
- 列出启动前必须满足的信息；
- 列出不应该启动的情况，例如测试提交、缺少关键字段、重复提交或人工暂停；
- 写清启动时传给流程的最小输入；
- 标记仍需人工决定的业务条件；
- 不设计后续销售流程；
- 不虚构表单字段、客户资格标准或权限规则；
- 不选择自动化平台。

## Step 5 — 复盘判断框架

must-retain judgments：
- 触发只负责“什么时候开始”，不能承担整个工作流设计；
- 时间、事件、人工启动都可以是合理触发方式；
- 只定义“什么时候启动”而没有“不启动条件”，容易产生误触发；
- 启动前必须具备后续第一步真正需要的最小输入；
- AI 可以帮助整理候选触发规则，但不能替业务决定哪些事件有权启动高风险流程；
- 重复事件需要被识别，但完整幂等与重复执行保护留到 T4-11。

## Step 6 — 能力获得

Capability Gain：
> 我能为一条工作流定义清楚的启动事件、必要条件、不启动条件和最小输入。

Self Assessment：
- 我能说清“发生什么才开始”，而不只是写一个模糊时间；
- 我能列出至少一种不应该启动的情况；
- 我能说清启动时第一步真正需要哪些信息。

Trigger Scenario：
> 当你已经把人工流程拆清楚，却发现自动化设计里只写了“每天跑一次”或“有消息就执行”时，这节课用于补上真正的启动边界，避免误触发和无效运行。

Next Lesson Value：
> 工作流启动以后，还需要持续知道“现在跑到哪里、发生过什么”；下一课进入状态与进度设计。

## Anti-repeat / boundary

- ≠ T4-02：T4-02 拆“做哪些步骤”，T4-03 只决定“什么时候开始”。
- ≠ T4-04：本课不维护运行中的状态。
- ≠ T4-11：这里只建立重复事件意识，不展开幂等保护。
- 不教 Cron 表达式、Webhook 编程、消息队列或平台 Trigger 配置。
- 不进入 OAuth、权限系统或生产部署。
