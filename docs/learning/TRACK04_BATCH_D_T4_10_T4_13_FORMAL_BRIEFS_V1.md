# Track 04 Batch D — T4-10～T4-13 Formal Briefs v1

Status: **RELEASED FORMAL BRIEF / HUMAN_REVIEW_PASS / AVAILABLE / FORMAL_RUNTIME / ACCEPTANCE_PASS**
Scope: **失败恢复 → 重复执行保护 → 人工确认 → 工作流与智能体边界**

## T4-10 — 外部调用超时或失败，流程应该怎么处理

Primary Knowledge Home: **超时 / 重试 / 失败恢复**
Learner result: 能为外部调用定义可重试、不可重试、停止和转人工的处理规则。

Core judgment: 重试不是“失败了再来一次”。先判断失败类型、是否可能恢复、重复执行是否安全，再决定重试、停止或人工处理。

Step 2：用“抓取新闻源失败 / 写入草稿失败 / 发布失败”比较。
Step 4：为内容发布链设计失败处理表。
Must-retain：
- 超时不等于一定失败，但不能无限等待。
- 暂时性失败与业务性拒绝要区分。
- 重试前先判断重复执行风险。
- 高风险写入失败不能盲目重试。
- AI 可分类错误和建议处理，不得自行无限重试或改业务数据。

Deferred：指数退避、队列、死信、补偿事务代码实现。

## T4-11 — 同一个动作执行两次，怎么避免造成两份结果

Primary Knowledge Home: **幂等（Idempotency）与重复执行保护**
Learner result: 能识别重复提交、重试和网络抖动导致的重复执行风险，并设计业务唯一标识与“已处理”检查。

Core judgment: 可靠自动化必须假设同一个事件可能来两次。关键不是“希望它别重复”，而是重复发生时结果仍可控。

Step 2：同一需求表单重复提交、同一文章重复建草稿。
Step 4：为“审核通过后写入公众号草稿”做重复保护设计。
Must-retain：
- 重复事件在真实系统里是常态风险。
- 关键动作执行前应检查唯一业务标识/已处理状态。
- 读操作和写操作重复风险不同。
- “发现重复后跳过”也要留下明确结果。
- AI 可辅助识别相似内容，但不能作为唯一去重依据决定不可逆写入。

Deferred：数据库唯一索引、分布式锁、事务工程。

## T4-12 — 哪些动作可以自动做，哪些必须先让人确认

Primary Knowledge Home: **人工确认 / 审批 / 回退**
Learner result: 能按风险、可逆性和责任确定人工确认点，并说明确认前后系统分别能做什么。

Core judgment: 人工确认不是每一步都加一个按钮，而是在高风险、不可逆或责任明确的动作前设置真正必要的控制点。

Step 2：内容发布、客户报价、客服高风险答复。
Step 4：为自媒体“草稿生成→事实核对→发布”设计人工确认点。
Must-retain：
- 可逆低风险步骤可以更自动化。
- 对外发布、金额承诺、权限变化等应有明确确认。
- 确认人必须看到做决定所需的证据。
- 拒绝/退回后要有明确下一步。
- AI 可整理证据和建议，不替责任人完成最终审批。

Deferred：IAM/RBAC、企业审批系统、审计日志实现。

## T4-13 — 固定流程不够用时，什么时候才需要智能体（Agent）

Primary Knowledge Home: **工作流与智能体的动态性边界**
Learner result: 能判断任务是否真的需要运行时动态决策，避免把稳定流程过度智能体化。

Core judgment: 能提前定义步骤和分支的任务优先固定工作流；只有路径必须根据运行中信息动态选择、且这种动态性有真实价值时，才考虑智能体。

Step 2：固定日报流程 vs 开放式研究任务。
Step 4：对三个真实业务任务做“固定工作流 / 有限动态决策 / 智能体候选”判断。
Must-retain：
- 智能体不是更高级的工作流。
- 可预定义步骤优先固定流程，更容易测试和控制。
- 动态决策必须有真实必要性。
- 智能体也需要停止条件、工具边界和人工控制。
- 不因为任务复杂就自动选择智能体。

Deferred：多智能体框架、规划算法、长期记忆系统。
