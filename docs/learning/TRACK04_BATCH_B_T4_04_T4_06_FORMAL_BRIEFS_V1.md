## T4-04 — 流程跑到哪一步了，系统怎么知道当前状态

Primary Knowledge Home: **状态与进度**
Learner result: 能定义一条工作流需要记住的最小状态，以及哪些事件会让状态发生变化。

### Core judgment
系统不能靠“看起来像做到哪了”猜进度。可靠流程要明确记录：当前处于什么状态、已经发生过什么、下一步允许发生什么。

### Step intent
1. 建立直觉：人能靠记忆补进度，系统必须显式记录。
2. 讲透方法：用 AI 日报“待收集→待筛选→待审核→可发布/已停止”比较状态和普通备注。
3. 检查理解：最佳状态设计 / “日志越多越等于状态越清楚”误区 / 最小状态边界。
4. 实操：为内容复用流程做“状态清单 + 状态变化条件 + 必要记录”。
5. 复盘：状态用于控制下一步，不是把所有历史文本都塞进去；AI 可协助整理，不应自行改业务状态。
6. 能力获得：遇到流程多步运行、需要恢复或多人协作时，能先设计状态而不是只写步骤。

### Step 5 must-retain judgments
- 状态是系统当前需要据此做决定的事实，不等于完整日志。
- 每个状态都应能回答“现在处于哪里”和“下一步允许什么”。
- 状态变化要由明确事件或判断触发，不能靠模型猜测。
- 失败、暂停、完成也属于需要表达的状态。
- AI 可以解释/整理状态信息，但最终业务状态写入必须受控。

### Deferred boundary
不教状态机框架、数据库字段设计、事件总线或长运行 Agent 工程。

## T4-05 — 什么时候继续、停止，什么时候算失败

Primary Knowledge Home: **继续 / 完成 / 停止 / 失败边界**
Learner result: 能为每个关键步骤写清继续条件、正常完成、主动停止和真正失败的区别。

### Core judgment
“不继续”不一定等于“失败”。可靠工作流必须区分：条件不足暂不继续、业务上主动停止、已经正常完成，以及系统真正出错。

### Step intent
1. 建立直觉：同样是“没往下走”，原因可能完全不同。
2. 讲透方法：用线索整理流程比较“资料不足等待补充 / 不符合范围主动停止 / 正常整理完成 / 外部调用报错”。
3. 检查理解：分辨停止与失败、完成条件、边界多选。
4. 实操：为客服答复流程设计继续/完成/停止/失败规则。
5. 复盘：失败不等于所有异常；AI 不替业务决定是否应该继续服务或停止。
6. 能力获得：遇到工作流分支复杂时，能先把退出边界定义清楚。

### Step 5 must-retain judgments
- 完成、停止、等待和失败必须分开。
- 业务条件不满足通常是停止/等待，不应伪装成技术失败。
- 失败必须有可观察依据，不能只写“结果不好”。
- 停止条件属于业务规则，AI 可辅助整理但不能私自决定高风险终止。
- 明确退出边界能避免无限循环和错误继续。

### Deferred boundary
不教重试实现、补偿事务、队列死信；这些在 T4-10 以后继续。

## T4-06 — 每一步到底需要看到哪些信息

Primary Knowledge Home: **节点级上下文治理**
Learner result: 能为工作流中的一个步骤区分“必须知道 / 有帮助但可缺省 / 不应该加载”的信息。

### Core judgment
上下文不是越多越好。每一步只应拿到完成当前职责所需的最小充分信息，避免无关信息、旧信息和敏感信息干扰判断。

### Step intent
1. 建立直觉：同一条业务链不同步骤需要的信息不同。
2. 讲透方法：用 AI 日报“收集 / 筛选 / 写观点 / 审核”比较各步所需信息。
3. 检查理解：最小充分信息 / “把所有资料一次给模型最好”误区 / 不该加载的信息。
4. 实操：为线索整理中的“判断是否需要人工跟进”设计上下文清单。
5. 复盘：上下文应服务当前步骤；AI 不该看到与任务无关的敏感或过期信息。
6. 能力获得：遇到模型输出漂移、上下文过长或多人流程时，能重新定义每一步该看到什么。

### Step 5 must-retain judgments
- 必须知道、可选信息、不应加载要分开。
- 当前步骤只加载完成职责所需的最小充分上下文。
- 事实来源要明确，旧信息和冲突信息不能静默混用。
- 敏感信息按需要最小化暴露。
- AI 可以利用上下文生成/判断，但不能决定自己应该获得哪些权限或敏感数据。

### Deferred boundary
不教向量数据库、RAG 工程、权限系统、Secret 管理或企业数据治理实现。
